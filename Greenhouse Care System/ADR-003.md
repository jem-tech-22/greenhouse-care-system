# ADR-003: Using SQLite for Sensor History Storage

## Status
Accepted

## Context
The Greenhouse Care System backend receives sensor readings from the ESP32 and provides data to the dashboard. The system needs to store historical temperature, humidity, water-level, and fan-status readings so they can be retrieved later.

The project uses a Node.js backend with Express and SQLite through the better-sqlite3 library.

## Decision
Use SQLite as the database for storing sensor history.

The backend stores the following information for each saved reading:

- Temperature
- Humidity
- Water level
- Fan status
- Low-water status
- Timestamp of the saved reading

The backend saves the first accepted reading after startup and then saves at most one history record every 60 seconds while the server remains running. The latest live reading is also maintained separately for the dashboard.

## Alternatives Considered
1. Store readings only in memory, which would lose historical data when the server restarts.
2. Use a separate database server, which would require additional setup and maintenance.
3. Use SQLite, which stores data in a local database file and works with the existing Node.js backend.

## Consequences

### Benefits
- Stores sensor history locally in `greenhouse.db`.
- Does not require a separate database server.
- Integrates with the existing Node.js backend through better-sqlite3.
- Allows the backend to retrieve recent saved readings.

### Trade-offs
- The database file must be backed up to protect historical data.
- The local database is tied to the machine or environment where the backend runs unless deliberately moved or shared.
- SQLite may be less suitable than a server-based database for applications requiring many concurrent writers or distributed database access.
